## 1. What "Arabic MVP" means

A customer in Egypt, Saudi Arabia or the Gulf can run the whole sales workflow (sign in, leads, properties, pipeline, viewings, deals, offers, commissions, documents, reports, settings) in **Arabic with a correctly mirrored layout**, switch language per user, and see the **basic user-visible errors in Arabic**.

### In the MVP

| Area | Included |
|---|---|
| Language | Arabic and English; per-user language with a company default; resolution before sign-in as in ADR-0001 |
| Layout | Full RTL mirroring of the 16 screens and shared components (shell, navigation, tables, forms, dialogs, toasts, pickers, calendar, custom charts) |
| Text | All static strings of the 16 screens and shared components from catalogs (about 580 strings plus dynamic sentences), with ICU plurals |
| Enums | Status, stage, type, source, role, category labels per entity (gender-correct) |
| Font and typography | IBM Plex Sans Arabic under `:lang(ar)`; Arabic typography rules |
| Numbers, currency, dates | `Intl`-based; formatting locale follows the user's language by default (ADR-0001 2.4); the 7 target currencies correct (including 3-decimal KWD/BHD/OMR); relative dates through `Intl.RelativeTimeFormat`; **company week start and weekend** (defaults from the company's region, overridable) and the **currency display option** (symbol or code): **in the MVP, but not in Phase 1** |
| API errors | The basic user-visible errors (sale rules, permissions, validation, authentication) translated through stable error codes (additive on the backend); unknown codes show a generic Arabic message plus the code |
| Mobile | Phone and tablet layouts correct in both directions |
| Tests | English E2E unchanged and green; the main flows also run in Arabic; geometry and overflow checks in both directions |

### Not in the MVP (decided or recommended)

| Item | Status |
|---|---|
| Arabic-Indic digits option | later, company setting; storage never changes |
| Hijri calendar display | optional and deferred; the base calendar stays Gregorian |
| Bilingual property content | deferred; no new fields or migrations |
| Activity and Notification storage as `kind` + `params` | **separate later phase**, and **not widened into Phase 1**. Until then, history lines stay in the language they were written in (English) inside an Arabic interface: a **known, temporary limitation accepted by the owner**. A screen that shows them is **not counted as fully translated** and is listed as "partially localized" in the release notes |
| Address model redesign, international phone normalization, Arabic-aware search | later phases; **not an automatic part of Phase 1 or of the MVP** (recommended soon after it) |
| Django admin in Arabic | no (operators only) |

## 2. MVP acceptance criteria (each one is checkable)

1. **First byte is right.** For a user with `language = ar`, the server-rendered HTML has `<html lang="ar" dir="rtl">`; switching language needs no manual reload and leaves no flash of the other language or direction. (Playwright: read the initial response HTML.)
2. **Resolution order.** Unit tests cover the full matrix of ADR-0001 (profile, cookie, company, `Accept-Language`, fallback `en`, invalid values ignored) and a page test covers the signed-out path.
3. **Persistence per user.** A language change survives sign-out/in and another device (once the backend field exists).
4. **No hard-coded UI strings** in migrated directories: the lint rule is an error there; a key-completeness check proves `en.json` and `ar.json` have the same keys, valid ICU and the same placeholders; no glossary term has two translations.
5. **Mirroring is real, not only the `dir` attribute.** Geometry assertions in `ar`: the sidebar is at the right edge, the mobile drawer opens from the right, toasts sit bottom-left, back/next arrows are flipped (computed transform), numeric table columns align to the end, the profile menu opens toward the inline start.
6. **No horizontal overflow** at 375 / 768 / 1280 px in `ar` and `en`, with the long Arabic fixtures already in the E2E setup and the pseudo-locale.
7. **Numbers and dates.** A table test of 7 currencies x (en, ar) x (latn) with expected strings (KWD/BHD/OMR three decimals); dates and relative time for fixed instants in `Africa/Cairo` (with DST) and `Asia/Riyadh`; week start and weekend for EG, SA, AE.
8. **Errors.** Every translated error code exists in both catalogs; each code is exercised by a test that triggers it through the API and checks the Arabic text; an unknown code never shows a raw English sentence or a technical field name.
9. **Bidi isolation.** Phone numbers, e-mail addresses, references and URLs render `dir="ltr"` inside RTL; names and titles are wrapped with `<bdi>`.
10. **English regression.** The English UI is visually and textually unchanged: the existing 188 E2E tests pass and a DOM-text snapshot of 6 routes is identical before and after each Phase 1 change.
11. **Budgets.** Arabic font transfer for a cold Arabic session <= ~200 KB (3 weights, Arabic + Latin subsets); no font request in an English session; one catalog per active language, <= 60 KB raw each.
12. **Accessibility basics.** `lang` and `dir` correct on `<html>`, accessible names (`aria-label`s) translated, focus order follows the visual order in RTL.
13. **Terminology.** The glossary passed an internal review before string extraction starts (Phase 3), and an Egyptian and a Saudi review before Arabic is released to customers; the open questions of the glossary are closed by then.
14. **Security.** The language cookie is validated against the allow-list; it carries nothing else.
