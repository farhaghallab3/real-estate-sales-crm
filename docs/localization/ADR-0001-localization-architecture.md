# ADR-0001: Localization architecture (Arabic / English, RTL / LTR)

* **Status:** Accepted in direction after the owner review of Phase 0 (2026-11-18). **Library decided on 2026-11-20: `next-intl@4.15.1`, pinned exactly** (section 2.1 and decision 8), after the Phase 1.1 dependency gate ([report](PHASE-1.1-DEPENDENCY-GATE.md)). The **font is still a candidate** that has to pass its Phase 2 gate. **Phase 1.1 was ACCEPTED by the owner on 2026-11-20** (decision 10): the dependency, the plugin, an empty catalog and a placeholder request config are in the working tree and verified on the real project, **with limitations**: ARM64 on real hardware untested, Vercel-style build run locally only, the 188 E2E run with a temporary copy of `stack.mjs` (two lines differ), and one known issue (KI-1, [gate report](PHASE-1.1-DEPENDENCY-GATE.md) section 13). Nothing is committed or deployed, and **no language behaviour changed**: the root layout still takes `lang`/`dir` from the company settings and nothing calls the library yet; the rest of this ADR (locale resolution, provider, catalogs) is design for later phases.
* **Scope:** the Next.js frontend, and the interface it expects from the backend later. No model, API or migration change is made or approved by this document.
* **Related:** [ADR-0002 Arabic font](ADR-0002-arabic-font.md), [Glossary](GLOSSARY-AR-EN.md), [MVP and Phase 1 plan](MVP-AND-PHASE-1-PLAN.md)

## 1. Context

Keystone CRM is sold to real-estate companies in Egypt, Saudi Arabia and the Gulf. Facts about the code today (audit, 2026-11-18):

* There is no i18n: about 580 static strings are written in English inside 41 TSX files (plus `constants.ts` labels), and the backend composes user-visible English text (58 error messages, 93 choice labels, 79 stored activity/notification messages).
* Groundwork exists: `CompanySettings` already has `language`, `locale`, `currency_code`; the root layout renders `<html lang dir>` on the server from `GET /api/config/`; money goes through one formatter (`useMoney`); the CSS is mostly `flex`/`gap`; about 90 direction-specific Tailwind classes are in 27 files and no logical (`ms-`, `pe-`, `text-start`...) classes are used yet.
* `language` is a property of the **company** (and only `en` is allowed by the backend). Mixed Arabic/English teams are normal in the Gulf, so it has to become a property of the **user**.
* The application is client-rendered behind a login (tokens in `localStorage`); 36 of the 41 TSX files are `"use client"`, data is fetched in the browser with React Query, there is no `middleware`, and the root layout is already `force-dynamic` because it reads the company config per request.

Decisions already taken by the product owner (inputs to this ADR): language per user with a company default; resolution before sign-in = locally saved language, then company language, then browser language, then English; Latin digits by default with an optional Arabic-Indic setting later, without changing how numbers are stored; week start and weekend per company, implemented in the calendar-formatting phase; Hijri optional and deferred, the base calendar stays Gregorian; Modern Standard Arabic, simplified and neutral; an open-licence self-hosted Arabic font; bilingual property content deferred (no new fields or migrations); E2E tests become less dependent on English text.

## 2. Decision

### 2.1 Library and routing mode

Use **`next-intl`** in its **"without i18n routing"** mode: **no `/ar/...` or `/en/...` URL prefixes, no middleware, no redirects.**

Why no prefixes: the app is behind a login (nothing to index), the URLs are used by the existing `rewrites` (`/api`, `/media`), by the E2E suite and by users' bookmarks; a prefix would touch all of them for no benefit. The locale comes from a cookie and the user profile, not from the path.

What `next-intl` gives that we do not want to write ourselves: ICU MessageFormat with plurals/select (Arabic has **six** plural categories: `zero one two few many other`, verified with `Intl.PluralRules("ar")`: 0 zero, 1 one, 2 two, 3-10 few, 11-99 many, 100+ other), typed message keys, server helpers for `generateMetadata`, and a provider for client components.

What we keep ours: **numbers, currency and dates keep going through our own `lib/format.ts` layer** (built on `Intl`), fed with the *formatting locale* of section 2.4. `next-intl`'s formatters are not used for money or dates, so the company's currency/numbering/calendar options stay in one place.

**Version (decided 2026-11-20): `next-intl@4.15.1`, pinned exactly** (no `^`/`~`; `use-intl` arrives with it at the same version, `4.15.1`). The decision comes from the Phase 1.1 dependency gate ([report](PHASE-1.1-DEPENDENCY-GATE.md)), which measured the candidates on the project's own Next.js 15.5.27 / React 19.3.0 and the repo's own Dockerfile.

| Option | Result of the gate | Verdict |
|---|---|---|
| **`next-intl@4.15.1`** | **Chosen.** +46 lockfile packages. Production build, standalone runtime smoke and SSR in both languages (`<html lang="en" dir="ltr">` / `<html lang="ar" dir="rtl">`, translated text in the first HTML) pass on **amd64 and on ARM64 under QEMU**. `npm audit`: adds no advisory. +≈45 KB on the production image, +≈12 kB first-load JS on a page that uses translations. Its two native packages exist **only at build time** (see below). | **Accepted.** |
| `use-intl@4.15.1` only (no Next plugin) | +7 pure-JS packages, no install scripts, no native code; same SSR result on amd64 (not run on ARM64: not needed once `next-intl` passed). Same +≈11 kB per translated page. Needs our own server-side locale and messages wiring (a small client wrapper around `IntlProvider`, cookie and catalog loaded in the root layout) and loses `getTranslations` in `generateMetadata`. | **Fallback**, kept ready (see "When to switch"). |
| `next-intl@4.4.0` (the former first candidate) | Pure JS (11 packages), but **flagged by `npm audit`** (two advisories, not exploitable in our no-middleware setup), eleven minor releases behind, and its caret ranges pull a newer `use-intl`/`icu-minify` than its own, so pinning it alone does not give a consistent set. | **Rejected.** Avoiding native dependencies is not a reason to run an older release. |

Why `next-intl` over `use-intl` for us:

* It is the official Next.js integration: the `createNextIntlPlugin` / `getRequestConfig` / `getLocale` / `getMessages` path of section 2.3 and `getTranslations` for `generateMetadata` come ready and typed, instead of being code we write and maintain around `IntlProvider`.
* The measured runtime and size cost is the same as the fallback's; the difference is supply-chain surface at build time only.
* It passed every check we could run, on both architectures.

**Install scripts and native dependencies: the risk, stated plainly.** `next-intl@4.15.1` brings `@swc/core@1.16.22` and `@parcel/watcher@2.6.0` as regular (non-optional) dependencies **with install scripts**, plus their per-platform binary packages and `@eloqnt/*`, `po-parser`, `next-intl-swc-plugin-extractor`. They belong to the message-extraction feature, which this project does **not** use.

* **Production:** none of it reaches the final image. The standalone production image (amd64 and ARM64) contains **no `@swc/core` and no `@parcel/watcher`** (the `@swc` folder holds only Next's own `helpers`), and not even `next-intl`/`use-intl` as folders (they are bundled into the server output). So there is no runtime, startup or image-size impact beyond the ≈45 KB above.
* **Build time:** the two install scripts run during `npm install` in the builder stage (and on every developer machine and CI runner). They ran and loaded successfully on Alpine amd64 (`linux-x64-musl`) and Alpine ARM64 (`linux-arm64-musl`); the builder `node_modules` grows by ≈19 MB compared with `use-intl`. The extra surface is real: two more packages that execute code at install time and a larger tree (46 vs 7 added packages) to keep audited.
* **Mitigation:** exact pin; committed lockfile; installs through the lockfile; the lockfile diff of the adding change is reviewed and must list exactly the expected packages; `npm audit` is part of the 1.1 acceptance.
* **Not tested:** whether the build still works with install scripts disabled for these two packages (the plugin does not need the extractor unless extraction is used), and the Windows and Vercel installs (listed as acceptance checks in the plan).
* **When to switch to `use-intl@4.15.1`:** if an install script fails or is blocked on a platform we must support (Windows developer machines, Vercel, a native ARM64 runner), or if the supply-chain surface becomes unacceptable. The switch is expected to be cheap (application code would use `useTranslations`-style APIs in both, and the fallback needs a small client provider wrapper); this was exercised only in the probe, not in the real app.

Peer ranges checked: `next ^15` (installed 15.5.27), `react ^19` (installed 19.3.0), TypeScript 5. All satisfied; Next.js stays at 15.5.27 for the localization work (its security update to 15.5.29 is a separate change, see the gate report).

### 2.2 Where the language comes from

Two different questions, answered separately.

**A. Signed-in user:** the saved preference of the user (`user.language`, a later backend field; `null` means "no preference") is the source of truth and travels across devices. The cookie below is only its local cache.

**B. Everyone else (login page, first visit, signed-out), and the signed-in user with no preference:**

1. the language saved **locally**: the first-party cookie `crm_lang` (`en` | `ar`);
2. the **company** default language (`GET /api/config/`, fetched once per request by the request-scoped `getCompany()` with `cache: "no-store"` and a 2.5 s timeout, decision 12);
3. the **browser** language (`Accept-Language`, negotiated against the supported list);
4. **English**.

The cookie is the "saved locally" mechanism on purpose, not `localStorage`: the server must know the language **before it renders**, and a server cannot read `localStorage`.

```
resolveLocale({ cookie, userLanguage, companyLanguage, acceptLanguage }):
  if userLanguage in SUPPORTED:           return userLanguage      # signed-in preference wins
  if cookie in SUPPORTED:                 return cookie
  if companyLanguage in SUPPORTED:        return companyLanguage
  match = negotiate(acceptLanguage, SUPPORTED)
  return match ?? "en"
```

Rules:

* `SUPPORTED = ["en", "ar"]` is one allow-list in one module; every input is validated against it (a tampered cookie can only ever select a supported language; the cookie holds nothing else and is not sensitive).
* Cookie: `crm_lang`, `Path=/`, `SameSite=Lax`, one year, `Secure` in production, **not** `HttpOnly` (the client sets it when the user switches). Changing language = write cookie + save to the profile (once that field exists) + `router.refresh()`.
* On sign-in the profile's language is written to the cookie *before* the first navigation, so the first screen is already in the right language.
* Another device changed the preference: the next profile fetch on this device updates the cookie and refreshes once (a brief switch of language on that device is accepted).
* Direction is derived from the language, not stored: `ar` -> `rtl`, `en` -> `ltr`. The company's `direction` field stays only as the direction of the company's default language.

### 2.3 SSR and hydration

* The root layout (already a dynamic server component) resolves the locale per request (`cookies()` and `headers()` are async in Next 15), then renders `<html lang={locale} dir={dir}>` and wraps the tree in `NextIntlClientProvider` with `{ locale, messages, timeZone }`. The first byte of HTML already has the right `lang`/`dir`: no flash and no client-side flip.
* `src/i18n/request.ts` (`getRequestConfig`) returns `{ locale, messages, timeZone }`. Messages are loaded with a dynamic import per locale (`messages/${locale}.json`), so **only the active language is shipped**; this works with `output: "standalone"` and on Vercel.
* Nothing server-rendered may format a date or number from the server's time zone and locale. Today this holds because data pages are client-fetched; the rule is: **dates and amounts are rendered from client-fetched data, or the provider gets an explicit `timeZone`**. A Phase 1 test renders the shell in both languages and fails on a hydration warning.
* `suppressHydrationWarning` is not used: server and client agree by construction (same cookie, same allow-list).
* `generateMetadata` uses `getTranslations` (title template, description); the company name stays untranslated.
* The existing `rewrites`, `skipTrailingSlashRedirect` and the `/api/config/` fetch are unchanged.

### 2.4 Language, formatting, currency, numbering and storage are different things

| Concept | Owner | Examples | Where it comes from |
|---|---|---|---|
| **Interface language** (words, plurals, direction) | the **user** | `ar` / `en` | section 2.2 |
| **Formatting locale** (separators, grouping, currency pattern, month names, week data) | **follows the user's language by default** | `ar-EG`, `en-EG`... | derived: the user's language + the region of `company.locale` (the existing setting stays as it is) |
| **Base currency** | the **company**, locked after financial data exists (existing rule) | `EGP`, `SAR`, `KWD` | `company.currency_code` (existing) |
| **Numbering system** | the **company**, as a setting for now | `latn` (default), `arab` | new company option, default `latn` |
| **Stored money values** | unchanged | decimals | **storage format and precision never change**; only the display does |

Owner decision (Phase 0 review): the formatting locale follows the user's language by default, currency and numbering stay company-level, and a **company-wide formatting override** (everybody sees the same pattern whatever their language) is *not* built now; it can be added later only if a real need appears. Practical effect today: with Latin digits the grouping and decimal separators of the target regions are the same in English and in Arabic (see the table below), so two users of the same company read an amount the same way; what differs is words (currency symbol or code, month names, "today"/"tomorrow").

Derivation used by `lib/format.ts` (one function, unit-tested):

```
region          = new Intl.Locale(company.locale).region                  # EG, SA, AE...
formattingLocale = new Intl.Locale(userLanguage,
                     { region, numberingSystem: company.numbering ?? "latn", calendar: "gregory" })
```

Real output of this derivation (Node 24 / ICU, 1,234,567.891 with the company's own currency):

| Company | Language | Result |
|---|---|---|
| ar-EG, EGP | en | `EGP 1,234,567.89` |
| ar-EG, EGP | ar | `‏1,234,567.89 ج.م.‏` |
| ar-SA, SAR | ar | `‏1,234,567.89 ر.س.‏` |
| ar-KW, KWD | en / ar | `KWD 1,234,567.891` / `‏1,234,567.891 د.ك.‏` (**three decimals**, same for BHD, OMR) |
| ar-EG, EGP, numbering `arab` (later option) | ar | `‏١٬٢٣٤٬٥٦٧٫٨٩ ج.م.‏` |
| ar-EG | ar, compact | `1.2 مليون ج.م.‏` |

Dates and relative time are produced by `Intl.DateTimeFormat` / `Intl.RelativeTimeFormat` (no hand-built "Today"/"ago" strings): e.g. `ar` gives `اليوم` / `غدًا` / `أمس` / `قبل 3 ساعات` / `خلال أسبوعين`; a Cairo timestamp in Arabic reads `18‏/11‏/2026، 4:30 م`. The Arabic UI uses the Gregorian calendar (Hijri is a later, optional display).

Week start and weekend (calendar phase): defaults come from CLDR through `Intl.Locale#getWeekInfo()` per company region (EG: week starts Saturday, weekend Fri-Sat; SA: starts Sunday, weekend Fri-Sat; AE: starts Monday, weekend Sat-Sun; KW: starts Saturday, weekend Fri-Sat) and become **company settings that can be overridden**. The calendar currently hard-codes Monday. Browsers without `getWeekInfo` use a small built-in table.

Open point for Phase 5: the Saudi riyal has a new currency symbol that many fonts do not contain yet; in Arabic the current ICU output uses the abbreviation `ر.س.‏`, in English the code `SAR`. The company-level option "currency display: symbol / code" must exist before the first Saudi customer.

### 2.5 Message catalogs

* `messages/en.json` is the source; `messages/ar.json` is translated by people (not machine-translated) using the [glossary](GLOSSARY-AR-EN.md).
* One JSON per language, namespaced by feature (`common`, `nav`, `auth`, `leads`, `properties`, `deals`, `pipeline`, `viewings`, `tasks`, `commissions`, `documents`, `reports`, `settings`, `notifications`, `errors`, `enums`).
* ICU MessageFormat everywhere a number or a name appears: **no string concatenation, no `count === 1 ? "deal" : "deals"`**. Arabic needs all six plural forms, e.g. `{count, plural, zero {لا صفقات} one {صفقة واحدة} two {صفقتان} few {# صفقات} many {# صفقة} other {# صفقة}}`.
* **Enum labels are translated per entity, never shared.** Arabic labels agree in gender with the noun (a *deal* "صفقة" is feminine, a *lead/client* "عميل" is masculine), so `Closed` for a deal and for a lead are two different keys (`enums.dealStage.closed`, `enums.leadStatus.closed`).
* Keys are typed from `en.json` (`AppConfig["Messages"]`), so a missing key is a compile error.
* Completeness checks in CI: same key set in both languages, valid ICU, same placeholders, no empty values, no glossary term translated two different ways (list in the glossary).
* A pseudo-locale (`en-XA`: accented, ~35% longer) is generated for layout tests.

### 2.6 Direction in the UI (summary; details in the Phase 2 plan)

Physical Tailwind classes (`ml/mr/pl/pr/left/right/text-left/text-right/border-l/...`) become logical ones (`ms/me/ps/pe/start/end/text-start/text-end/border-s/...`); icons that point somewhere get `rtl:-scale-x-100`; Arabic typography overrides live under `:lang(ar)` (no `tracking-*`, no `uppercase`, larger minimum size). User content that is not language-bound (phone numbers, e-mail, references such as `PR-00042`, URLs) is isolated with `dir="ltr"`, names/titles with `<bdi>`.

### 2.7 What the backend will have to offer (design only, not approved, not started)

* `User.language` (nullable) and the allow-list `LANGUAGES = ("en", "ar")` in company settings.
* API errors carry a stable machine `code` plus `params`, so the frontend shows its own translated text; the basic user-visible errors are part of the **Arabic MVP** (see the plan). Unknown codes show a generic Arabic message plus the code, never a raw English sentence or a technical field name.
* Activity/Notification storage as `kind` + `params` is a **separate, later phase**. Until then, stored history lines stay in the language they were written in (English); the interface around them is Arabic. This is a known, documented limitation of the MVP.
* Django admin stays English (operators only).

## 3. Alternatives considered

| Alternative | Why not |
|---|---|
| `next-intl` with locale-prefixed routing + middleware | URL, rewrite, E2E and bookmark churn with no SEO benefit behind a login. |
| `i18next` / `react-i18next` | Capable, but less integrated with the App Router and server rendering; more glue for typed keys. |
| `react-intl` (FormatJS) | Fine ICU support, but no App Router/server story comparable to `next-intl`. |
| Own dictionary + small `t()` | Arabic plurals/gender need ICU; we would rebuild it badly. |
| Company-wide language only | Does not fit mixed Arabic/English teams (decision 1). |
| `localStorage` for the saved language | Not readable on the server before render; would cause a flash of the wrong language and direction. |

## 4. Consequences

* A new runtime dependency (`next-intl@4.15.1`, MIT) with 46 added lockfile packages (MIT, Apache-2.0, BSD-3-Clause), two of them native build-time packages with install scripts (section 2.1), and, in dev, a unit-test runner for the pure functions (locale resolution, formatting derivation): **`vitest@5.1.1`, exact, dev only (added in Phase 1.2; decision 11)**.
* Every string in the migrated screens leaves the code; a lint rule stops new hard-coded strings in migrated directories.
* The E2E suite today depends on little English text (about 11 text locators: "Add lead", "Sign in", "Main", "Company", `/Leads/`, "Open menu"); they move to roles with accessible names from the catalog and a few `data-testid`s.
* Bundle: one catalog per active language only; estimated well under 60 KB raw for ~600 strings per language.
* The English UI must stay visually identical (the Arabic font is applied under `:lang(ar)` only).

## 6. Risks and open questions

1. **Translation quality** (real-estate terminology differs between Egypt and the Gulf): mitigated by the glossary and a review by one Egyptian and one Saudi reader before release.
2. **History lines in English** in the Arabic UI until the later Activity/Notification phase: **accepted by the owner as a known, temporary limitation.** A screen that shows them is *not* counted as fully translated (it is listed as "partially localized" in the release notes), and Phase 1 does not widen to redesign that storage.
3. **Saudi riyal symbol** font support: decide display mode (symbol vs code) in Phase 5.
4. **`getWeekInfo` support** in all target browsers: built-in fallback table.
5. **Company time zone**: the backend uses UTC and the browser shows local time; monthly/daily report boundaries per company time zone were not verified and are outside this ADR.
6. **Cookie vs profile drift** between devices: accepted (one refresh).
7. **Install scripts and native packages of `next-intl@4.15.1`** (`@swc/core`, `@parcel/watcher`, build time only): see section 2.1. The Windows install/build check passed and the Vercel-style build passed locally (not on Vercel itself); the fallback is `use-intl@4.15.1`.
8. **Probe is not integration:** the gate proved the library, the build and SSR of `lang`/`dir` in a copy of the layout with a probe page. It did not prove the integration with the real layout, the company config, the auth provider or the E2E suite. *(Update 2026-11-21: the integration with the real layout, the company config, the auth provider and the E2E suite was proven in Phase 1.3, decision 12; the E2E independent of English text was started in Phase 1.6 (decision 15) and stays partial until Phase 3 replaces its temporary strings table with catalogue reads.)*
9. **Real ARM64 hardware** was not available: ARM64 was proven only under QEMU emulation. A smoke on a native ARM64 runner (the OCI target) is recommended before the first customer release.
10. **Known issue KI-1 (webpack cache warnings from `next-intl`'s message extractor):** three non-fatal warnings per production build (**intermittent: absent in the Phase 1.3b build, three in the Phase 1.4 build, two in the Phase 1.5 build**) and two in a short `next dev` session; no observed impact; not suppressed by decision; revisit at every `next-intl` upgrade and in the Phase 1.8 close-out. Full text, conditions and what is unproven: [gate report](PHASE-1.1-DEPENDENCY-GATE.md) section 13.

## 7. Decision log (owner review of Phase 0, 2026-11-18)

1. **Vitest** is adopted for the pure i18n unit tests (dev dependency only).
2. **`next-intl@4.4.0` is the first candidate, not a final decision.** The Dependency Gate (Phase 1.1) compares it with a current release and decides; native dependencies are measured, not avoided by reflex. *(Superseded by decision 8: the gate was run and decided.)*
3. **IBM Plex Sans Arabic** is the candidate font; the final choice follows a visual review in Phase 2, with **Noto Sans Arabic** as the fallback ([ADR-0002](ADR-0002-arabic-font.md)).
4. **Old Activity/Notification lines stay in English for now** (known limitation); a screen showing them is not "fully translated"; Phase 1 does not redesign their storage.
5. **Week start, weekend days and the currency display option are in the Localization MVP, not in Phase 1.**
6. **Glossary review:** an internal review first (before string extraction), then an Egyptian and a Saudi review before Arabic is released to customers.
7. **Formatting (architecture):** currency stays per company; numbering system stays a company setting for now; **the formatting locale follows the user's language by default**; a company-wide formatting override may be considered later if a real need appears; **stored financial values and their precision never change**.
8. **Library (owner decision, 2026-11-20, after the Phase 1.1 gate):** **`next-intl@4.15.1`, pinned exactly**, replaces "first candidate 4.4.0". `next-intl@4.4.0` is rejected (flagged by `npm audit`, behind, version skew); `use-intl@4.15.1` stays the documented fallback. The native packages (`@swc/core`, `@parcel/watcher`) are accepted as a **build-time-only** risk, proven absent from the production images. Open conditions before Phase 1.1 is complete: Windows native install/build and Vercel-style build ([plan](MVP-AND-PHASE-1-PLAN.md)); real ARM64 hardware is recommended before a customer release. Next.js stays at 15.5.27 for this work; its security update is a separate change. *(Update 2026-11-20: that Next.js update to 15.5.29 was done as its own change and passed `npm audit`, typecheck, lint, build, a Docker amd64 build with smoke and the 188 E2E.)*
